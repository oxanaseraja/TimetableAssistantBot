# Процессы и функциональность TimetableAssistantBot

## Обзор продукта

**TimetableAssistantBot** — это автоматизированный помощник для групповых чатов, который распознаёт упоминания времени в сообщениях и автоматически показывает это же время в часовых поясах всех участников канала. Это решает проблему координации между людьми из разных часовых поясов, избавляя от необходимости вручную пересчитывать время.

**Ценность для пользователей:**
- Экономия времени — не нужно вручную пересчитывать время
- Снижение ошибок — автоматический расчёт исключает человеческие ошибки
- Улучшение коммуникации — все участники сразу видят время в своём часовом поясе

---

## Архитектура решения

Бот построен по принципу **чистого разделения ответственности**:

- **Ядро (Core)** — платформо-независимая логика обработки времени. Не знает о Telegram, Discord или других платформах. Работает только с данными.
- **Адаптер (Adapter)** — мост между платформой (Telegram) и ядром. Преобразует события платформы в формат, понятный ядру, и форматирует ответ для пользователей.

Такая архитектура позволяет легко добавлять поддержку новых платформ (Discord, WhatsApp) без изменения логики обработки времени.

## Подробный процесс обработки сообщения

### Этап 0: Инициализация бота (при запуске)

**Что происходит:**
1. Бот загружает конфигурацию из `configuration.yaml`
2. Загружает справочник городов из `data/cities.json` (например, "Amsterdam" → "Europe/Amsterdam")
3. Загружает профили пользователей и каналов из `data/users.json`
4. Подключается к Telegram API
5. Начинает слушать новые сообщения в указанном чате

**Результат:** Бот готов к работе, все справочники загружены в память для быстрого доступа.

---

### Этап 1: Получение сообщения от пользователя

**Что происходит:**
Пользователь отправляет сообщение в Telegram-чат, например: `"See you at 10:30 Amsterdam"`

**Технические детали:**
- Telegram отправляет событие в бот через API
- Адаптер получает событие с полями:
  - Текст сообщения
  - ID пользователя (например, `123`)
  - ID чата (например, `-1001`)
  - ID сообщения (например, `555`)
  - Временная метка сообщения (UTC)
  - Флаг: это новое сообщение или редактирование

**Результат:** Адаптер получил сырое событие от платформы.

---

### Этап 2: Преобразование события платформы во внутренний формат

**Что происходит:**
Адаптер преобразует Telegram-событие в универсальный формат, который понимает ядро.

**Процесс:**
1. **Анонимизация ID:** Все платформенные ID преобразуются в хеши (SHA256) для безопасности и универсальности:
   - `telegram_user_id: 123` → `internal_user_id: SHA256("telegram:123")`
   - `telegram_chat_id: -1001` → `internal_channel_id: SHA256("telegram:-1001")`
   - `chat_id:message_id: -1001:555` → `internal_message_id: SHA256("-1001:555")`

2. **Создание события ядра:**
   ```
   CoreMessageEvent {
     internal_message_id: "abc123...",
     internal_user_id: "def456...",
     internal_channel_id: "ghi789...",
     text: "See you at 10:30 Amsterdam",
     is_edit: false,
     timestamp_utc: "2026-01-25T12:00:00Z"
   }
   ```

3. **Загрузка контекста пользователя и канала:**
   - Адаптер ищет профиль пользователя в `users.json` по `internal_user_id`
   - Адаптер ищет контекст канала в `users.json` по `internal_channel_id`
   - Если пользователь не найден, создаётся пустой профиль (без часового пояса)
   - Если канал не найден, создаётся пустой контекст

**Результат:** Ядро получает полностью анонимизированное событие и контекст, не зная о платформе.

---

### Этап 3: Обнаружение времени в тексте

**Что происходит:**
Ядро анализирует текст сообщения и ищет упоминания времени с помощью **строго определённых правил** (regex-паттернов).

**Поддерживаемые форматы времени:**

1. **24-часовой формат:** `10:30`, `09:05`, `23:59`
2. **12-часовой формат с AM/PM:** `10:30am`, `1pm`, `9 AM`, `12:00 p.m.`
3. **Час без минут с триггерным словом:** `at 8`, `by 3`, `в 10` (только если есть слово-триггер)

**Процесс обнаружения:**
1. Ядро применяет три regex-паттерна по приоритету
2. Если найдено несколько совпадений, выбирается первое по позиции в тексте
3. Максимум обрабатывается 3 упоминания времени (остальные игнорируются для защиты от спама)

**Примеры:**
- `"See you at 10:30 Amsterdam"` → найдено: `10:30` (24-часовой формат)
- `"Call at 8"` → найдено: `8` (час без минут, **неоднозначно** — может быть 08:00 или 20:00)
- `"Meeting at 2pm"` → найдено: `2pm` (12-часовой формат)

**Важно:** Ядро **не использует** LLM или эвристики. Только точные паттерны. Если время не распознано — бот молчит.

**Результат:** Список найденных упоминаний времени (или пустой список, если ничего не найдено).

**Остановка процесса:** Если время не найдено → ядро возвращает `None` → адаптер не отправляет ответ.

---

### Этап 4: Извлечение подсказки о часовом поясе

**Что происходит:**
Ядро ищет в тексте сообщения подсказки о часовом поясе, чтобы понять, в каком часовом поясе указано время.

**Источники подсказок (в порядке приоритета):**

1. **Явное указание смещения UTC/GMT:** `UTC+2`, `GMT-5`, `+0300`, `+3`
2. **Явное указание IANA-идентификатора:** `Europe/Amsterdam`, `America/New_York`
3. **Название города из whitelist:** `Amsterdam`, `NYC`, `London` (только города из `cities.json`)

**Процесс поиска:**
1. Ядро берёт контекст вокруг найденного времени (±30 символов)
2. Проверяет наличие подсказок по приоритету
3. Если найдено несколько подсказок одного приоритета, выбирается ближайшая к упоминанию времени
4. Если подсказка не найдена, используется следующий этап (профиль пользователя/канала)

**Примеры:**
- `"See you at 10:30 Amsterdam"` → найдено: `Amsterdam` → `Europe/Amsterdam`
- `"Meeting at 2pm UTC+3"` → найдено: `UTC+3` → `+03:00` (приоритет выше, чем город)
- `"Call at 10:30"` → подсказка не найдена → переход к профилю пользователя

**Результат:** Часовой пояс для исходного времени (или `None`, если не определён).

---

### Этап 5: Разрешение часового пояса (если подсказка не найдена)

**Что происходит:**
Если в тексте не найдено явной подсказки о часовом поясе, ядро использует контекст пользователя и канала.

**Правила разрешения (в порядке приоритета):**

1. **Часовой пояс пользователя** — из профиля автора сообщения
2. **Часовой пояс канала по умолчанию** — из настроек канала
3. **Единственный активный часовой пояс** — если в канале только один участник с известным часовым поясом
4. **Системный часовой пояс по умолчанию** — UTC (если не настроен другой)

**Процесс:**
1. Ядро проверяет каждый источник по порядку
2. Если источник даёт валидный часовой пояс → используется он
3. Если все источники исчерпаны и остаётся неопределённость → ядро возвращает `None`

**Примеры:**
- Пользователь из `Europe/Amsterdam`, подсказки нет → используется `Europe/Amsterdam`
- Пользователь без часового пояса, канал по умолчанию `America/New_York` → используется `America/New_York`
- Пользователь без часового пояса, в канале 3 участника с разными часовыми поясами, подсказки нет → **неоднозначность** → ядро возвращает `None`

**Результат:** Часовой пояс для исходного времени или признак неоднозначности.

**Остановка процесса:** Если часовой пояс не может быть однозначно определён → ядро возвращает `None` → адаптер не отправляет ответ.

---

### Этап 6: Проверка на неоднозначность

**Что происходит:**
Ядро проверяет, может ли время быть интерпретировано однозначно.

**Причины неоднозначности:**

1. **Час без минут и без AM/PM:** `"at 8"` может быть 08:00 или 20:00
2. **Несколько возможных часовых поясов:** Пользователь не указал часовой пояс, а в канале несколько участников с разными часовыми поясами
3. **Несколько упоминаний времени с разными контекстами:** (В MVP обрабатывается только первое)

**Правило безопасности:**
> Если есть любая неоднозначность → бот молчит. Лучше не ответить, чем ответить неправильно.

**Результат:** Признак неоднозначности (`HIGH` или `NONE`).

**Остановка процесса:** Если неоднозначность = `HIGH` → ядро возвращает `None` → адаптер не отправляет ответ.

---

### Этап 7: Конвертация времени в часовые пояса участников

**Что происходит:**
Ядро конвертирует найденное время во все активные часовые пояса канала.

**Процесс:**
1. Ядро берёт исходное время в определённом часовом поясе (например, `10:30 Europe/Amsterdam`)
2. Определяет список активных часовых поясов канала (из профилей участников)
3. Конвертирует время в каждый часовой пояс с учётом:
   - Смещения UTC
   - Перехода на летнее/зимнее время (DST) — используется дата сообщения как референс
4. Ограничивает результат максимум 5 часовыми поясами (защита от спама)

**Пример:**
```
Исходное: 10:30 Europe/Amsterdam (UTC+1)
Активные часовые пояса: [Europe/Amsterdam, Asia/Yerevan, America/Vancouver]

Результат:
- 10:30 Europe/Amsterdam (UTC+1)
- 13:30 Asia/Yerevan (UTC+4)
- 02:30 America/Vancouver (UTC-8)
```

**Важно:** Конвертация учитывает переход на летнее/зимнее время автоматически, используя стандартную библиотеку Python `zoneinfo`.

**Результат:** Список конвертированных времён для каждого часового пояса.

---

### Этап 8: Формирование ответа

**Что происходит:**
Ядро формирует структурированный ответ, который адаптер затем отформатирует для пользователя.

**Структура ответа:**
```
DisplayBlock {
  entries: [
    {
      timezone: "Europe/Amsterdam",
      local_time: "10:30",
      cities: []  // заполняется адаптером
    },
    {
      timezone: "Asia/Yerevan",
      local_time: "13:30",
      cities: []
    }
  ],
  ordering: "SOURCE_FIRST",  // порядок сортировки
  flags: {
    ambiguous: false,  // была ли неоднозначность
    partial: false     // были ли отброшены часовые пояса из-за лимита
  }
}
```

**Правила сортировки:**
1. Исходный часовой пояс (где указано время)
2. Часовой пояс канала по умолчанию (если отличается)
3. Остальные по смещению UTC (по возрастанию), затем по алфавиту

**Результат:** Структурированный объект `DisplayBlock` или `None` (если обработка остановилась на предыдущих этапах).

---

### Этап 9: Форматирование ответа для пользователя

**Что происходит:**
Адаптер преобразует структурированный ответ ядра в читаемый текст для Telegram.

**Процесс:**
1. Адаптер берёт `DisplayBlock` от ядра
2. Для каждого часового пояса:
   - Форматирует время в 24-часовом формате (`HH:MM`)
   - Ищет города в `cities.json`, которые относятся к этому часовому поясу
   - Формирует строку: `{HH:MM} {timezone_id} (City1, City2)`
3. Объединяет строки (максимум 5 строк)
4. Сортирует по правилам из `DisplayBlock.ordering`

**Пример форматирования:**
```
10:30 Europe/Amsterdam (Amsterdam)
13:30 Asia/Yerevan (Yerevan)
02:30 America/Vancouver (Vancouver)
```

**Результат:** Текст для отправки в Telegram.

---

### Этап 10: Отправка ответа пользователю

**Что происходит:**
Адаптер отправляет отформатированный ответ в Telegram как ответ на исходное сообщение.

**Процесс:**
1. Адаптер вызывает Telegram API для отправки сообщения
2. Сохраняет ID ответа в памяти (для обработки редактирований)
3. Если отправка не удалась (сетевые ошибки) → повторяет попытку до 3 раз с задержкой 500мс

**Обработка ошибок:**
- Сетевые ошибки (5xx) → повторные попытки
- Ошибки авторизации (4xx) → логирование и остановка бота
- Ошибки ядра → логирование, пользователю ничего не отправляется

**Результат:** Пользователь видит ответ с временем в разных часовых поясах.

---

## Обработка редактирований сообщений

**Что происходит:**
Если пользователь редактирует сообщение, бот обновляет свой ответ.

**Процесс:**
1. Адаптер получает событие редактирования от Telegram
2. Удаляет предыдущий ответ бота (если он существует)
3. Обрабатывает отредактированное сообщение заново (этапы 2-10)
4. Отправляет новый ответ (или ничего, если время удалено или стало неоднозначным)

**Примеры:**
- Пользователь меняет `"at 10:30"` на `"at 11:30"` → бот обновляет ответ
- Пользователь удаляет время из сообщения → бот удаляет свой ответ
- Пользователь меняет `"at 2pm"` на `"at 8"` (неоднозначно) → бот удаляет ответ

## Текущий функционал (MVP)

### ✅ Реализовано

1. **Распознавание времени:**
   - 24-часовой формат (`10:30`)
   - 12-часовой формат с AM/PM (`2pm`, `10:30am`)
   - Час без минут с триггерными словами (`at 8`, `by 3`)

2. **Определение часового пояса:**
   - По явным подсказкам в тексте (UTC/GMT смещения, IANA ID, города)
   - По профилю пользователя
   - По настройкам канала
   - По активным часовым поясам участников

3. **Конвертация времени:**
   - Автоматический учёт перехода на летнее/зимнее время
   - Поддержка всех стандартных часовых поясов (IANA)

4. **Обработка событий:**
   - Новые сообщения
   - Редактирования сообщений

5. **Защита от ошибок:**
   - Молчание при неоднозначности
   - Молчание при отсутствии времени
   - Обработка сетевых ошибок с повторными попытками

6. **Ограничения для защиты от спама:**
   - Максимум 3 упоминания времени на сообщение
   - Максимум 5 часовых поясов в ответе
   - Обработка только первого найденного времени (MVP упрощение)

   - `"через час"`, `"через 2 часа"`

3. **Поддержка диапазонов времени:**
   - `"10:00-11:00"`, `"с 9 до 10"`
   - Показ времени начала и конца в разных часовых поясах

4. **Поддержка дат:**
   - `"25 января в 10:30"`, `"Jan 25 at 10:30"`
   - Конвертация с учётом конкретной даты

5. **Интерактивные диалоги:**
   - Если время неоднозначно, бот может спросить уточнение

6. **Поддержка других платформ:**
   - Discord
   - WhatsApp
   - Slack

7. **Персонализация:**
   - Пользователи могут настроить свой часовой пояс через команды бота
   - Сейчас: часовые пояса задаются администратором в `users.json`

8. **Расширенная аналитика:**
   - Статистика использования
   - Наиболее частые часовые пояса
   - История конвертаций

9. **Поддержка удаления сообщений:**
   - Автоматическое удаление ответа бота при удалении исходного сообщения
   - Сейчас: ответ остаётся, даже если исходное сообщение удалено

10. **Поддержка потоков (threads):**
    - Обработка сообщений в отдельных потоках обсуждения
    - Сейчас: только основное сообщение

## Ограничения и известные проблемы

### ⚠️ Текущие ограничения

1. **Только первый часовой пояс:**
   - Если в сообщении несколько времён, обрабатывается только первое
   - Остальные игнорируются

2. **Нет поддержки относительного времени:**
   - `"через час"`, `"завтра"` не распознаются
   - Только абсолютное время

3. **Нет поддержки дат:**
   - `"25 января в 10:30"` не распознаётся
   - Время всегда интерпретируется относительно даты сообщения

4. **Жёсткие правила распознавания:**
   - Только точные паттерны, никаких вариаций
   - `"10.30"` (точка вместо двоеточия) не распознаётся
   - `"полдесятого"` не распознаётся

5. **Требуется ручная настройка:**
   - Часовые пояса пользователей задаются администратором
   - Нет автоматического определения часового пояса

6. **Один чат на бота:**
   - Бот работает только в одном указанном чате
   - Не поддерживает несколько чатов одновременно

## Технические детали для понимания масштабируемости

### Производительность

- **Обработка одного сообщения:** < 100мс (синхронная обработка)
- **Память:** ~10-50 МБ (зависит от размера справочников)
- **Пропускная способность:** Ограничена только лимитами Telegram API (30 сообщений/сек)

### Надёжность

- **Обработка ошибок:** Все ошибки логируются, пользователю ничего не показывается
- **Повторные попытки:** Автоматические при сетевых ошибках
- **Состояние:** Хранится в памяти, теряется при перезапуске (кроме опциональной персистентности ID)

### Безопасность

- **Анонимизация ID:** Все платформенные ID хешируются перед передачей в ядро
- **Токены:** Хранятся только в переменных окружения, не в коде
- **Валидация входных данных:** Строгая валидация всех входных данных перед обработкой

## Заключение

TimetableAssistantBot — это автоматизированное решение для координации времени в групповых чатах. Бот работает по принципу "лучше промолчать, чем ошибиться" — если время неоднозначно или не распознано, бот просто не отвечает, чтобы избежать путаницы.

Текущая версия (MVP) покрывает основные сценарии использования и готова к продуктивному использованию. Будущие версии расширят функциональность для более сложных случаев и добавят поддержку других платформ.
